## 1. 今天的证据链（logs/lan-20261108-102215）

| 环节 | 结果 | 证据 |
| --- | --- | --- |
| 元数据注入 | ✅ 生效 | `detail/app/5164`、`detail/app/2078` 三次响应被改写（`update_injected: ALL`） |
| 商店采纳 | ✅ | 商店改用替换包哈希（`7d04db26…`）去取签名 |
| 下载替换 | ✅ | 14 轮下载全部返回 `Content-Range: bytes …/19,042,758`（DiPlay 大小），官方原包是 231,623,624 B |
| 安装 | ❌ 被拦 | 每轮下载后商店反复重下（10:36 → 10:53 共 14 轮），没有一次装成功 |

**关键发现：一轮下载里商店查了两次签名，第二次查的是「APK 文件自己」的身份：**

```text
10:36:15  sign(packageName=com.zeekr.media.qq, apkVersion=1931091890, sha=7d04db26…)  ← 元数据身份（注入的版本号）
10:36:16  sign(packageName=com.shihab.diplay,  apkVersion=41,         sha=7d04db26…)  ← 文件真实身份
10:36:16  sign(packageName=com.zeekr.media.qq, apkVersion=1931091890, sha=7d04db26…)
10:36:19  sign(packageName=com.shihab.diplay,  apkVersion=41,         sha=7d04db26…)
```

`com.shihab.diplay / 41` 与 DiPlay 0.2.22 的真实包名、真实 versionCode 完全一致（apktool 核对：`versionCode: 41, versionName: 0.2.22`）。

**结论：商店（`x-app-version: 57`）在安装前会解析下载回来的 APK，按文件自身的 包名 + versionCode + 哈希 再向服务端鉴权一次。**
服务端只按哈希认官方包 → 第三方 APK 永远 `sign:null` → 安装授权不通过 → 提示「商城以外的应用」。

也就是说：**v1.0.0 依赖的漏洞 B（更新路径不校验 sign）已经被收紧**。旁证：接口版本从 10-30 的 `v2/app/appList` 变成今天的 `v1/app/appList`，商店/系统这周变过。

> 现在这条链的三道门：① 元数据哈希一致（已绕过）② 下载内容哈希一致（已绕过）③ **文件身份的签名（新门）**。

## 2. 本轮顺手挖到的三个新攻击面

| # | 发现 | 证据 | 能干什么 |
| --- | --- | --- | --- |
| A | **下载 CDN 完全不鉴权**，且支持 Range | Mac 上直接 `Range: bytes=0-0` 拿到 `Content-Range: bytes 0-0/231623624`，无需任何 token/签名头 | 在 Mac 上按需 Range 取商店任意 APK 的中央目录/单个 entry，不必整包下载：`scripts/apk-range.py` |

## 3. 实验阶梯（车机旁边 1–3 分钟一轮，按顺序试）

插件已经加好开关（`scripts/test-addon.py` 已离线验证）。启动方式：

```bash
./venv/bin/python lan_sideload.py artifacts/DiPlay-0.2.22.apk <开关>
```

| 编号 | 假设 | 命令开关 | 判读 |
| --- | --- | --- | --- |
| **E1** | 商店只判 `sign` 是否非空 | `--sign nonempty` | 装上 → 门只是"非空"，**立刻恢复侧载** |
| **E2** | 商店验签但不校验绑定 | `--sign any`（回放真签名）<br>`--sign pkg`（回放同包真签名） | 装上 → 可以用"真签名 + 我们的内容"长期绕过；E1 失败 E2 成功 → 本地有公钥验签但不绑哈希 |
| **E3** | 存在免签/白名单类型 | `--sign-type 1`、`--sign-type 2`（配合 `--sign any`） | `signType` 也许表示"无需签名/第三方"，服务端与商店对它处理不同 |
| **E4** | 内容校验与签名校验用不同字段 | `--hash-fields md5`（sha256 留官方值）<br>`--hash-fields sha256`（md5 留官方值） | `md5` 能装 → 内容只比 md5，那 `sha256` 就能保持官方值 → 签名天然有效，不用伪造任何东西（最干净的绕法） |
| **E5** | 元数据里有"三方/发布类型"开关 | `--patch '"publishType":1,"devType":1,"dataType":0,"supportUninstall":1'` | 逐个二分，找到能改变安装行为的那个字段 |
| **E6** | 商店「打开」照抄服务端给的组件名 | `--launch-activity com.android.settings/.Settings`（或车机上的工程模式组件） | 能拉起设置/工程页 → 打开「未知来源 / ADB」，改走真正的安装路径（比跟签名较劲更彻底） |
| **E7** ⭐ | 鉴权认的是「包名是不是商店的应用」 | `scripts/repackage.sh <apk> --as <商店收录包名> [--version-code N] [--name 显示名]` → 再 `--sign any` | **已在 Mac 上跑通**：DiPlay 换壳成 `com.zeekr.media.qq`（只改包名不改类名、17 个组件全部在 dex 里、自签 v1+v2+v3）。已装且签名不同的包会撞签名 → 先卸载它（QQ音乐 `supportUninstall:1`）或挑「收录但未装」的包 |
| **E8** | 直接读商店的安装鉴权代码 | 用 MT管理器 把 `com.zeekrlife.market` 的 `base.apk` 拷到 `/sdcard`，再 FTP 到 Mac | `jadx` 反编译：搜「商城以外」定位拦截点、看它是否本地验签、找 exported 组件和 H5 桥 —— **最决定性的一步** |

真签名会自动缓存到 `logs/<本次运行>/sign-cache.json`（商店打开任意官方应用详情页时就会喂进来一次），`--sign pkg/any` 直接用它。
也可以手动指定：`--sign literal --sign-value 'file:///tmp/sign.txt'`。

### E1/E2 的正确操作顺序（避免踩"版本号缓存"坑）

1. 启服务 → 车机**点开一个官方应用的详情页**（喂一次真签名进缓存）；
2. 回到要伪装的应用详情页 → 点更新/安装；
3. 终端应依次出现 `[sign-cache]`、`[inject-update]`、`[sign] … -> 改写为 mode=…`、`[replace-apk] 以 … 替换下载`；
4. 记下**车机上的原话和第几步弹的**（这是分辨门在哪的唯一依据）。

### 6.1 官方 QQ音乐（app 5164）的真实身份 —— 全程不碰车机

| 字段 | 官方值 | 取证方式 |

| versionCode / versionName | **167** / `1.6.7` | 同上 |
| minSdk / targetSdk | **28** / **34** | 同上 |
| 大小 / md5 | 261,893,737 B / `9b095c89…`（CDN 文件名就是 md5） | `--list` 中央目录 |
| v1 签名文件 | **没有**（META-INF 根目录无 `.RSA/.SF/.DSA`，只有第三方库自带的 MANIFEST.MF）→ 官方包是 **v2/v3-only 签名** | `--list` |
| `launcherActivities` | `com.zeekr.media.qq.app.ZeekrActivity` | `detail/app/5164` 响应体 |

对照：app 2078（浏览器 `com.zeekr.broswer`）= `/app-market/apk/1750040710746/bc4ce18b….apk`，231,623,624 B。

### 6.2 又抓出一个没排除过的变量：版本号不一致

失败那轮（`logs/lan-20261108-102215`）注入后的元数据是 `apkVersion=1,931,091,890 / apkVersionName=9.9.890`，
而 APK 文件自身的 `versionCode=41`（DiPlay 真实值）。商店在安装前会**解析文件、按文件身份再查一次签名**（见 §1），
所以「元数据版本号 ≠ 文件版本号」本身就可能是拒绝理由 —— **之前从没排除过它**。
结论：把壳做得除了哈希以外和官方一模一样，只留「sha256 不是官方」这一个变量，判读才干净。

### 6.3 E7 重做：身份一致的壳（已产出、已离线回归）

```bash
./scripts/repackage.sh artifacts/DiPlay-0.2.22.apk --as com.zeekr.media.qq \
  --version-code 168 --version-name 1.6.8 --min-sdk 28 --target-sdk 34 --name DiPlay \
  --out "artifacts/DiPlay-0.2.22@com.zeekr.media.qq-vc168.apk"
```

成品 `artifacts/DiPlay-0.2.22@com.zeekr.media.qq-vc168.apk`：
`19,261,818 B` · `sha256 b17a82ae…` · `md5 4b6cb1e0…` · 包名/168/1.6.8/28/34 全部与请求一致 · 17 个组件 dex 里缺失 0 个 · 自签（`CN=ZEEload`，cert sha256 `d71d3b8e…`）。
`168 > 官方 167`，商店才会把它当「有更新」。

**顺手修掉 `repackage.sh` 一个真 bug**：apktool 会把 `versionCode/versionName` 从 manifest 挪到 `apktool.yml`，
原来那段 manifest 正则**改不到它**，成品会静默用回原版本号（第一次产出的壳 `versionCode` 还是 41，靠 aapt2 复查才发现）。
现在 manifest + `apktool.yml` 两边都改，新增 `--min-sdk/--target-sdk`，并加了一道「成品身份必须等于请求值」的硬校验（不一致直接 FAIL 退出）。

离线回归（拿真实 `detail/app/5164` 响应体喂 `_inject_update`）：注入后元数据 =
`com.zeekr.media.qq / 168 / 1.6.8 / sha256 b17a82ae… / md5 4b6cb1e0… / size 18.37`，下载地址武装到官方 `9b095c89….apk`。✔

**下一轮的 E7 命令**（`--pkg` 收窄到 QQ音乐，`--patch` 把版本号钉成 168，和壳文件一致）：

```bash
./venv/bin/python lan_sideload.py "artifacts/DiPlay-0.2.22@com.zeekr.media.qq-vc168.apk" \
  --pkg com.zeekr.media.qq --sign any --patch '"apkVersion":168,"apkVersionName":"1.6.8"'
```

| 壳=QQ音乐 `com.zeekr.media.qq` v168 | `--sign any --patch apkVersion=168` | **静默转圈**，一个签名查询都没发 | 商店在用缓存元数据/下载队列，我们的注入没被采纳 |
| 壳=浏览器 `com.zeekr.broswer` v10031（当时已装） | `--sign pkg`（回放浏览器**自己**的真签名） | 下载 19,261,818 B 成功 → 重试 5 轮 → 退回「下载」 | 见下方机制 |
| 壳=腾讯云游戏 `com.tencent.gamereva.car` v6021696（**车上从未装过**，排除签名冲突） | `--sign any` | 同上，重试 5 轮 | 不是签名冲突问题 |
| 同上 | `--hash-fields md5`（**sha256 保持官方值**，只改 md5） | 商店查询仍带**我们文件的 sha256** → 服务端 null | **校验用的是商店自己从下载文件算出来的 sha256，不是元数据里的字段** |
| 同上 | `--patch publishType=1,devType=1,dataType=1` | 字段确实下发为 1，仍重试 | 这三个字段不控制这道校验 |

**另外排除**：`launcherActivities` 劫持（E6）—— 改成 QQ音乐 的启动组件之后点「打开」，起来的还是浏览器本尊，
说明「打开」用的是本地 PackageManager，不信服务端下发的组件名。（改成 `com.android.settings/.Settings` 会让详情页**渲染空白**，但那是渲染层的毛病，不是它在解析组件名。）

### 7.3 机制结论（现在有直接证据）

> **商店下载完成后自己计算 APK 的 sha256，用「文件自身的 packageName + versionCode + sha256」去
> `/v2/app/signature` 换签名；服务端只登记官方包的哈希，第三方内容永远返回 `sign:null` → 拒绝安装。**

推论：

- 元数据里的 `sha256`/`apkMd5` 改成什么都不影响这次鉴权（鉴权用的是实测文件哈希）。
- **回放真签名（哪怕同包同版本、哪怕 344 字完整格式）也无效** —— 那份签名是签给官方哈希的，
  对我们自己的内容不成立。所以 E1（伪造非空）、E2（回放真签名）不用再试了，已被证据覆盖。
- 换壳（改包名+versionCode）确实**打掉了**「不能安装非应用商店安装的应用」那句提示
  —— 后续所有轮次都变成了「下载成功但反复重下」，没有再弹过原话。也就是说
  **原来的那句话是「文件身份不在商店目录里」的提示，换壳解决的正是这一层**；
  剩下的这道门是「文件哈希必须在服务端登记」，第三方内容过不去。
- v1.0.0 在 7X 上能成、在 5.6d 上不能成，差别就在这一道哈希登记，不是签名算法变了。

### 7.4 顺带确证的两件事

- `apkSign` 这个元数据字段**服务端对所有应用都给字面量 `"sign"`**（14 条官方条目逐个核对过）
  → 上游插件写死 `"sign"` 和官方一致，不是失败原因。
- 商店的**搜索接口不走被劫持的两个域名**，所以搜索行为在我们的流量里完全不可见。

### 7.5 剩下的路（按性价比）

1. **E8 反编译商店本体**（`com.zeekrlife.market`）：读到那段校验就能确定有没有可关的分支、
   `signType` 有没有免签取值、有没有别的安装入口。取 APK 的两条途径：
   商店自己若在目录里（搜「商店」→ 详情页 → 我们抓 apkUrl → CDN Range 直读，不碰车机）；
   否则只能 adb 从车机取 `base.apk`。
2. **车机侧拿 ADB / 未知来源**：工程模式、连点版本号、拨号盘工程码——
   一旦拿到，`adb install` 直接结束战斗，完全不碰这套鉴权。
3. **E3 `signType`**（还没试，但按 7.3 的机制，光改 signType 大概率没用）。
4. 已排除：E1、E2、E4、E5（publishType/devType/dataType）、E6、E7（单靠换壳）。

## 8. 11-08 下午后半段：漏洞 A 还在，能撬的远不止商店那道门

前面 §7 的结论成立（商店 UI 那条路按文件自身 sha256 鉴权，第三方内容过不去）。但商店只是**极氪后端的一个业务**，
我们手里那条能解密的 TLS 链覆盖的是**整机对极氪后端的调用**。把已有捕获重新过一遍，翻出这些之前没注意的东西：

### 8.1 我们实际在做中间人的范围（两个域名，但业务远不止商店）

`snc-api-gw.zeekrlife.com`（310 次）+ `snc-download-cdn.zeekrlife.com`（175 次），路径族包括：
`app-market/*`（商店）、`browser-service/*`（浏览器）、`weather/*`、`fence-api-service/*`、
`uc/user-service/*`、`operationPoint/openApi/protocol/info`、`zmusic/*`、`user-aigc-service/*`、`scenario-*` 等。

### 8.2 第二条安装通道：应用 OTA（最有戏）

- 接口：`/app-market/openserver/clientApi/v1/ota/update/appList`，已捕获 3 次（13:37:43、13:38:30 由车机发）
- 请求头 `okhttp/4.10.0`、`x-app-version: 57` —— **和商店同一个 App**，即商店内部有两条独立安装路径
- 请求体：车机上报**整机已安装包列表**（`appPackageNames` + `appPackageMd5`）——这是判断「车上装过什么」的唯一硬证据
  ⚠️ 之前内联副本截到 1200 字，列表被切掉（曾据此误判 QQ音乐 未安装）。已修：请求体完整存盘为 `<时间>-<接口>-req`
- 响应：13 项预装/系统应用（含 `com.zeekr.managerapplication` 车机管家、`com.ecarx.usermanual` 用户手册、
  `com.zeekr.media.qq` v145 等），下载地址是 `/app-market/apk/<ts>/<md5>.apk` 这一族
- **关键观测：全部 67 次签名查询只涉及 3 个包（浏览器 / 腾讯云游戏 / QQ音乐），这 13 项一次都没被查过签名**
  → 这条路的校验很可能与商店 UI 那条不同（待 E9 实测，不能只凭"没查到"下结论）

### 8.3 浏览器是服务端驱动的（E10，成本最低的一扇门）

- `/browser-service/api/v1/navigation` 和 `/collection` 的响应**直接决定车机浏览器显示哪些网址**
  （捕获到的就是车主自己的收藏：UniFi、Musish、Music Assistant…）→ **我们可以往里加任意 URL**
- 于是可以不装任何 APK，先试 `intent://` 深链拉系统页面（Chromium 系浏览器认这个）
- 已实现：`--nav '名称|URL'`（可重复）+ `h5/index.html` 控制台 + `scripts/serve-h5.sh`
  控制台每点一次发 `tap=<名字>`，1.5 秒后再发 `still=<名字>`：**只见 tap 不见 still = 真的跳走了**；
  页面还会把 userAgent 打回来，直接判出浏览器内核（认不认 intent://）
- 顺带：`/browser-service/api/v1/blacklist` 返回一个 `downloadUrl` 指向 `snc-download.zeekrlife.com/.../black_list.db`
  —— **第三个域名还没劫持**；DNS 在我们手里，随时可以加记录把更多域名指过来

### 8.4 这台车的实际目录（20 个应用，全部官方）

由 appList / detail / ota 三处合并而来。要点：
`com.thunder.carplay` 其实是 **雷石KTV**（不是 CarPlay），目录里**没有**官方 CarPlay 方案；
